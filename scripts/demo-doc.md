# AI Agent Platform 도입 보고서

사내 업무 자동화를 위한 통합 Agent Runtime 의 6개월 파일럿 결과와 전사 확산 계획을 정리한다.

# 요약

## 파일럿은 목표를 초과 달성했다

운영팀·CS팀 2개 조직, 12명이 6개월간 AgentDure 파일럿을 운영했다. 반복 업무 처리량은
7.5배로 늘고 처리 시간은 45분에서 3분으로 줄었으며, 오류율은 십분의 일이 됐다.
파일럿 범위에서 장애로 인한 업무 중단은 없었다.

:::metrics
- 99.99% 가용성
- 43% 비용 절감
- 7.5x 처리량
:::

이 보고서는 파일럿의 정량 결과(4장), 운영·보안 체계(5장), 분기별 확산 계획(6장)을
담는다. 결론은 하나다 — **전사 확산을 승인해 달라.**

## 핵심 지표

| 지표 | 도입 전 | 도입 후 | 변화 |
|---|---:|---:|---:|
| 건당 처리 시간 | 45분 | 3분 | -93% |
| 일일 처리량 | 120건 | 900건 | +650% |
| 오류율 | 2.1% | 0.2% | -90% |
| 운영 인력 투입 | 5.0 FTE | 1.5 FTE | -70% |

측정 기준: 2026년 1월~6월, 운영팀 접수 처리 업무. 산출 방식은 부록에 있다.

# 도입 배경

## 반복 업무가 팀의 시간을 잠식하고 있었다

접수·분류·전달이 모두 수동으로 이루어졌다. 담당자는 하루 평균 4시간을 티켓 분류와
시스템 간 복사·붙여넣기에 썼고, 시스템마다 인터페이스가 달라 처리 이력이 흩어졌다.

- 접수·분류·전달이 모두 수동 — 건당 평균 45분
- Jira·Slack·사내 ERP 가 각각 다른 인터페이스
- 처리 이력이 세 시스템에 흩어져 감사 추적 불가
- 담당자 부재 시 처리 지연이 고객 이탈로 이어짐

## 기존 접근은 왜 실패했나

두 차례의 자동화 시도가 있었다. RPA 는 화면이 바뀔 때마다 깨졌고, 규칙 기반 봇은
예외 케이스 앞에서 멈췄다.

| 접근 | 기간 | 결과 |
|---|---|---|
| RPA 매크로 | 2024 하반기 | UI 변경마다 중단, 유지보수 비용이 절감분 초과 |
| 규칙 기반 봇 | 2025 상반기 | 정형 케이스 60%만 처리, 예외는 전부 수동 |

공통 원인은 **판단이 필요한 지점에서 자동화가 멈춘다**는 것이었다. LLM 기반 Agent 는
바로 그 지점을 다룬다.

# 아키텍처

## 전체 구조

![Agent Runtime을 중심으로 한 전체 구조](asset://architecture.png)

모든 도구 호출은 MCP(Model Context Protocol)로 표준화된다. Agent 는 도구의 구현을
모르고, 도구는 Agent 의 판단 로직을 모른다 — 이 분리가 시스템 추가 비용을 상수로
만든다.

## 구성 요소

### Control Plane

정책, 권한, 감사 로그를 관리한다. 어떤 Agent 가 어떤 도구를 쓸 수 있는지, 어떤
작업에 사람의 승인이 필요한지를 선언적으로 정의한다.

### Data Plane

Agent 실행과 도구 호출을 담당한다. 실행 단위는 Kubernetes Pod 이고, 도구는 MCP
서버로 연결된다.

```ts
const agent = new Agent({
  tools: await mcp.discover("agent-mcps"),
  policy: controlPlane.policyFor("ops-triage"),
});
await agent.run(task);
```

### Audit Store

모든 판단과 도구 호출을 불변 로그로 남긴다. "왜 이 티켓이 이렇게 분류됐나"에 로그
한 줄로 답할 수 있다.

## 인증 방식 선택

:::comparison
### IRSA

- 표준 방식, 넓은 생태계 지원
- 어노테이션 기반 설정
- 신뢰 정책을 Role 마다 관리

### Pod Identity

- 간단한 설정, 신규 권장
- 클러스터 단위 관리
- EKS 1.24 이상 필요
:::

신규 클러스터는 Pod Identity 로 통일하고, 기존 워크로드는 마이그레이션 없이 IRSA 를
유지한다. 두 방식의 권한 정책은 동일한 Terraform 모듈에서 생성된다.

# 도입 결과

## 정량 효과

비용 절감의 대부분은 인력 재배치에서 왔다. 5.0 FTE 가 하던 일을 1.5 FTE 가 감독하는
구조가 되면서, 3.5 FTE 는 판단이 필요한 고부가 업무로 이동했다.

| 항목 | 연간 효과 |
|---|---:|
| 인력 재배치 | 3.5 FTE |
| 처리 지연으로 인한 이탈 감소 | 매출 1.2% 방어 |
| 야간·주말 무인 처리 | 응답 SLA 24h → 1h |

## 현장의 반응

> 도입 후 반복 업무가 사라지고, 팀은 판단이 필요한 일에 집중하게 됐다. 특히 야간
> 접수가 아침에 이미 분류돼 있는 것이 체감 효과가 크다.

— 운영팀 리드

## 남은 문제

- 비정형 첨부파일(스캔 이미지)의 인식률이 82%에 머문다 — 4분기 개선 예정
- Agent 판단에 대한 이의 제기 절차가 아직 수동이다
- 피크 시간대 도구 호출 지연이 간헐적으로 2초를 넘는다

# 운영과 보안

## 권한 모델

Agent 는 사람과 같은 방식으로 권한을 받는다 — 최소 권한, 역할 기반, 만료 있는 자격.

- 도구별 허용 목록: Agent 는 정책에 선언된 MCP 도구만 호출할 수 있다
- 파괴적 작업(삭제·발송·결제)은 사람의 승인 단계를 강제한다
- 자격 증명은 Vault 에서 실행 시점에 주입되고 로그에 남지 않는다

## 감사와 추적

모든 실행은 Audit Store 에 다음을 남긴다: 입력, 판단 근거, 호출한 도구와 인자,
결과, 소요 시간. 감사팀은 대시보드에서 임의 건을 재구성할 수 있다.

# 확산 계획

## 분기별 로드맵

1. Q1 파일럿 2개 팀 운영
2. Q2 보안 검토와 권한 모델 확정
3. Q3 고객 접점 3개 조직 확산
4. Q4 전사 배포와 운영 이관

각 분기 말에 지표를 재측정해 다음 단계 진행 여부를 결정한다. 중단 기준은 오류율
1% 초과 또는 보안 사고 1건이다.

## 리스크와 대응

| 리스크 | 가능성 | 대응 |
|---|:---:|---|
| LLM 비용 급증 | 중 | 모델 티어링, 캐시 적중률 목표 60% |
| 오분류로 인한 고객 불만 | 중 | 신뢰도 임계값 미달 건 사람 검토 |
| 특정 벤더 종속 | 낮 | MCP 표준화로 모델·도구 교체 가능 |

# 부록

## 용어

| 용어 | 정의 |
|---|---|
| MCP | Model Context Protocol — Agent 와 도구 사이의 표준 인터페이스 |
| Control Plane | 정책·권한·감사를 관리하는 계층 |
| FTE | Full-Time Equivalent, 전일 근무 환산 인력 |
